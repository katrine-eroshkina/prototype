# Блочная система и технологии

Рабочий документ проекта. Версия от 18.10.2026, черновик: состав блоков и схемы страниц уточняются после анализа конкурентов и согласования карты сайта.

---

## 1. Источники и приоритеты

- **Бриф с созвона** — основной источник.
- **PDF-схема** — набросок, используем только как подсказку по наполнению.
- Все расхождения между ними фиксируем отдельно и согласуем с заказчиком.

## 2. Главная идея

Мы проектируем **систему блоков**, а не набор уникальных страниц.

```
Страница = Шаблон (каркас) + последовательность блоков + контент
```

Цель: заказчик сам собирает новые разделы из готовых блоков по инструкции, без дизайнера.

## 3. Иерархия услуг

```
Услуги
├── Консалтинг
│   ├── Маркетинговый аудит
│   ├── Маркетинговые консультации
│   ├── Маркетинговая стратегия
│   ├── Подбор маркетингового персонала
│   ├── Оценка подрядчиков
│   ├── Маркетолог под ключ
│   ├── Удалённый отдел маркетинга
│   ├── Стратегические сессии
│   ├── Брендинг
│   └── Презентации
└── Digital
    ├── SEO-продвижение        → услуги (SEO-аудит, …)
    ├── Контекстная реклама    → услуги (Директ, …)
    ├── Продвижение на Avito   → услуги
    ├── SMM                    → услуги
    ├── Таргетированная реклама → услуги
    ├── Продвижение в нейросетях → услуги
    └── Разработка сайтов      → услуги
```

- Вложенность в Digital: **категория → услуга**.
- В Консалтинге услуг меньше, поэтому уровень категорий там может не понадобиться. Можно сгруппировать: «Аудит и стратегия», «Команда», «Бренд».

## 4. Шаблоны (каркасы страниц)

В шаблоне зафиксированы шапка, тип первого экрана, хлебные крошки и подвал. Середина собирается из блоков.

| # | Шаблон | Где используется |
|---|---|---|
| T1 | **Главная** | `/` |
| T2 | **Листинг** | Каталог услуг, направление (Консалтинг / Digital), категория, список кейсов, блог, регионы |
| T3 | **Детальная** | Услуга, кейс, регион, «О компании», «Цены» |
| T4 | **Контакты** | `/kontakty/` (можно не выделять в шаблон и собрать на T3) |
| T5 | **Текстовая** | Политика, оферта, статья блога |
| T6 | **Системная** | 404, «Спасибо за заявку» |

## 5. Глобальные элементы

Есть на всех страницах или вызываются отовсюду:

- **Шапка.** Логотип, меню, переключатель языка, телефон или мессенджер, кнопка заявки.
- **Мега-меню «Услуги»** с двумя колонками: Консалтинг и Digital.
- **Мобильное меню.**
- **Подвал.** Навигация, контакты, реквизиты, юридические ссылки.
- **Поп-ап с формой заявки.**
- **Хлебные крошки.**
- **Плашка cookie.**

## 6. Библиотека блоков (черновой состав)

У каждого блока есть **тема фона** (`light` / `dark` / `accent`) и, где нужно, **варианты**.

### Первые экраны
| ID | Блок | Назначение | Варианты |
|---|---|---|---|
| `hero-main` | Главный экран | Манифест агентства, сразу задаёт характер | — |
| `hero-page` | Экран внутренней страницы | Заголовок, подзаголовок, CTA, крошки | с медиа / без |
| `hero-split` | Экран с формой | Для посадочных услуг: оффер + форма | — |

## 7. Схемы страниц (черновые)

Порядок блоков сверху вниз. Это стартовые наборы, а не жёсткие правила.

- **Главная (T1):** `hero-main` → `directions` → `manifesto` → `stats` → `cases` → `process` → `expert` → `clients` → `testimonials` → `cta-form`
- **Направление, например Digital (T2):** `hero-page` → `services-grid` → `situations` → `comparison` → `cases` → `lead-magnet` → `faq` → `cta-form`
- **Категория, например SEO (T2):** `hero-page` → `services-grid` → `situations` → `process` → `pricing` → `cases` → `cross-sell` → `faq` → `cta-form`
- **Услуга, например SEO-аудит (T3):** `hero-split` → `situations` → `includes` → `process` → `pricing` → `case-metrics` → `cross-sell` → `faq` → `cta-form`
- **Кейс (T3):** `hero-page` → `case-story` → `case-metrics` → `text-media` → `testimonials` → `cases` → `cta-banner`
- **О компании (T3):** `hero-page` → `manifesto` → `stats` → `team` → `documents` → `testimonials` → `cta-form`
- **Цены (T3):** `hero-page` → `pricing` → `comparison` → `faq` → `cta-form`
- **Контакты (T4):** `hero-page` → `contacts` → `cta-form`

## 8. Правила компоновки (черновик, войдёт в инструкцию)

1. Страница начинается с первого экрана (`hero-*`), а последний блок перед подвалом — `cta-form` или `cta-banner`.
2. Блоки одной темы фона не ставим больше двух подряд, темы нужно чередовать.
3. Два блока с сеткой карточек не ставим подряд.
4. CTA (форму, баннер или кнопку в блоке) показываем не реже одного раза на 3–4 блока.
5. `faq` ставим ближе к концу страницы, перед финальным CTA.
6. На странице услуги обязательно есть `pricing` или `cta-form`.
7. Блок `manifesto` ставим не больше одного раза на странице.
8. У каждого блока в каталоге указаны лимиты текста: длина заголовка, число карточек и т. д. Лимиты считаем с запасом под английский язык.
9. На первом экране нет всплывающих окон. Допускаются только cookie-плашка снизу и один чат или мессенджер (см. docs/02).
10. Цифры в кейсах и `stats` всегда указываем с базой или периодом. Голые «+500 %» не используем.
11. Каждая страница одного направления содержит `cross-sell` в другое направление.
12. На странице категории обязателен `services-grid` с дочерними услугами.

### Что фиксируем в каталоге по каждому блоку
- Назначение: когда использовать и когда не использовать.
- Обязательный и необязательный контент.
- Лимиты: символы в заголовке и подзаголовке, минимум и максимум элементов.
- Варианты и темы фона.
- Поведение на мобильных устройствах.
- Живой пример.

## 9. Мультиязычность

- Сейчас ориентируемся на российский рынок, позже на США. Скорее всего, будет отдельный сайт на том же дизайне.
- Сразу закладываем:
  - шрифты с кириллицей и латиницей;
  - запас по длине строк (английский текст бывает короче, но часть слов длиннее);
  - переключатель языка в шапке;
  - разделение контента по языкам (`ru/`, `en/`).
- В коде используем встроенную маршрутизацию Astro `/ru/` и `/en/`. При переезде английской версии на отдельный сайт меняется только конфиг.

## 10. Технологии

### Стек
- **Astro** работает на Vite. На выходе статический HTML/CSS почти без JS.
- **CSS-переменные** служат дизайн-токенами: цвета, типографика, отступы, радиусы, сетка.
- **JS** нужен только для интерактива: меню, слайдер, аккордеон, поп-ап. Пишем на чистом JS или точечно на React, если понадобится.
- **Контент** храним в Content Collections, это markdown или JSON-файлы.
- **Деплой** на GitHub Pages через официальный экшен `withastro/action`. Заказчику отправляем ссылку.

### Почему Astro
- Блок — это компонент с параметрами: `<Pricing theme="dark" packages={...} />`.
- **Страница — это файл со списком блоков.** Чтобы сделать новый раздел, достаточно создать файл, в котором перечислены блоки и их контент. Это и даёт заказчику возможность собирать разделы самостоятельно.
- Готовую чистую HTML-разметку из сборки можно перенести в любую CMS.
- Мультиязычность встроена.

### Как страница описывается в контенте (пример)
```yaml
---
title: SEO-аудит
direction: digital
category: seo
template: detail
blocks:
  - type: hero-split
    title: "Найдём, почему сайт не растёт"
  - type: includes
    theme: light
    items: [...]
  - type: pricing
    theme: dark
    packages: [...]
  - type: cta-form
---
```

### Структура репозитория (план)
```
src/
  styles/tokens.css       — дизайн-токены
  components/ui/          — атомы (Button, Tag, Input, Card…)
  components/global/      — Header, Footer, MegaMenu, Modal…
  blocks/                 — блоки (Hero, Pricing, Faq…)
  layouts/                — шаблоны T1–T6
  content/                — услуги, кейсы, блог… (ru / en)
  pages/                  — маршруты
  pages/blocks.astro      — каталог блоков и инструкция
docs/                     — проектная документация
```

### GitHub Pages: нюансы
- Если репозиторий проектный, сайт будет жить по адресу `username.github.io/repo/`. В конфиге нужно указать `site` и `base`, а все внутренние ссылки строить с учётом `base`.
- Позже можно подключить свой домен: тогда добавляем файл `CNAME` и убираем `base`.
- Формы на GitHub Pages сами не работают, потому что сервера нет. Для прототипа делаем заглушку со страницей «Спасибо», в продакшене форму подключат разработчики.

### Перенос в Figma
- Токены переносим в Figma Variables под теми же именами.
- Каждый блок становится компонентом. Свойства варианта называются так же, как параметры в коде (`theme`, `variant`, `columns`).
- Шаблоны собираем как фреймы из компонентов блоков.
- Переносим после утверждения визуала или параллельно с вёрсткой блоков.
